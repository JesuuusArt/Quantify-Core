# Catálogo de requisitos

**Estado:** propuesta de desarrollo. **Fuente:** [visión del producto](../../README.md), [Práctica 05](../Practica05/README.md) y [Práctica 07](../practica-07/README.md). Los identificadores RF son estables; los criterios AC aquí definidos son el objetivo de pruebas futuras.

## Funcionales

| ID | Necesidad e historia | Criterios de aceptación mínimos | Dependencias |
|---|---|---|---|
| RF-01 · Identidad | Como usuario quiero acceder y recuperar mi cuenta para conservar mi historial entre dispositivos | **AC-01.1:** una sesión válida permite usar recursos propios; una inválida se rechaza. **AC-01.2:** registro/recuperación siguen Keycloak; la API no guarda contraseñas. **AC-01.3:** usuario no puede asignarse rol administrador. **AC-01.4:** cierre de sesión y suspensión se verifican contra la política de revocación elegida | Decisión de sesión web y configuración de Keycloak |
| RF-02 · Perfil y consentimiento | Quiero administrar preferencias y finalidades autorizadas para controlar el uso de mis datos | **AC-02.1:** perfil incluye zona horaria de negocio válida. **AC-02.2:** IA y cada fuente biométrica son opcionales y se registran por finalidad y versión. **AC-02.3:** revocar bloquea usos futuros y tareas pendientes antes de ejecutarse. **AC-02.4:** cambiar zona no reclasifica silenciosamente el historial | RF-01; política de datos |
| RF-03 · Hábitos | Quiero crear, editar, pausar y archivar hábitos para organizar una rutina | **AC-03.1:** nombre, meta, unidad y frecuencia se validan en API y cliente. **AC-03.2:** edición versiona meta/frecuencia desde una fecha efectiva. **AC-03.3:** pausa y archivo conservan registros; el archivo bloquea nuevas marcas y avisos. **AC-03.4:** cancelar no crea ni cambia un hábito | RF-01/02; reglas de agenda |
| RF-04 · Registros | Quiero registrar progreso parcial y corregirlo para mantener evidencia fiel | **AC-04.1:** existe un resultado diario consolidado por hábito y fecha de negocio. **AC-04.2:** reintentar la misma operación no duplica progreso ni eventos. **AC-04.3:** origen, instante de ocurrencia/recepción y revisión quedan trazados. **AC-04.4:** una edición concurrente obsoleta se informa como conflicto; no se pierde silenciosamente | RF-03; contrato de idempotencia |
| RF-05 · Métricas y rachas | Quiero consultar historial, cumplimiento y rachas para entender mi progreso | **AC-05.1:** se aplican frecuencia y meta históricas, con versión de reglas. **AC-05.2:** un día no programado o pausado no cuenta como incumplimiento. **AC-05.3:** periodo sin oportunidades muestra «sin datos», no 0% de fracaso. **AC-05.4:** correcciones actualizan agregados y hacen visible si hay recálculo pendiente | RF-03/04; definición de métricas |
| RF-06 · Recordatorios | Quiero elegir avisos y horarios para recordar mi rutina | **AC-06.1:** se valida horario, zona, canal y días compatibles. **AC-06.2:** desactivar/archivar impide nuevos envíos. **AC-06.3:** reintentos no generan avisos duplicados para la misma ocurrencia/canal. **AC-06.4:** denegar permisos del dispositivo mantiene utilizable el registro manual | RF-02/03; proveedor de entrega pendiente |
| RF-07 · Recomendaciones | Quiero comprender y aceptar o descartar sugerencias para ajustar mi rutina | **AC-07.1:** consentimiento y suficiencia de datos se verifican al generar y servir resultados. **AC-07.2:** se muestran evidencia, ventana, versión y limitaciones. **AC-07.3:** solo guardar explícitamente la propuesta crea un hábito; cancelar no la acepta. **AC-07.4:** aceptar dos veces no duplica el hábito. **AC-07.5:** datos insuficientes o modelo deshabilitado generan abstención explicada | RF-02/03/04/05; evaluación de reglas/modelo |
| RF-08 · Dispositivos y biometría | Quiero vincular una fuente compatible y revocarla para enriquecer mis métricas voluntariamente | **AC-08.1:** vinculación prueba pertenencia y capacidades. **AC-08.2:** ingesta valida consentimiento, unidad, tiempos, esquema y duplicados por fuente. **AC-08.3:** desvincular impide nueva ingesta y uso de credenciales previas. **AC-08.4:** ausencias o señales inválidas no se interpretan como valor cero | RF-01/02; prueba Wear OS, SDK y permisos pendientes |
| RF-09 · Administración | Como administrador quiero mantener catálogo y acceso a cuentas para operar el servicio | **AC-09.1:** cada mutación exige permiso, motivo y auditoría. **AC-09.2:** editar/pausar plantilla solo afecta futuras incorporaciones. **AC-09.3:** suspensión bloquea operaciones según política de sesión verificada. **AC-09.4:** interfaces administrativas y API no exponen rutinas privadas por defecto. **AC-09.5:** proteger la continuidad administrativa antes de suspender cuentas privilegiadas | RF-01; política de acceso y catálogo |
| RF-10 · Auditoría y derechos de datos | Quiero conocer y gestionar mis datos; el equipo necesita trazabilidad operativa | **AC-10.1:** mutaciones sensibles registran actor, acción, recurso, resultado y motivo cuando corresponda. **AC-10.2:** exportar requiere identidad verificada, acceso exclusivo y caducidad. **AC-10.3:** eliminación sigue un estado trazable por almacén, derivados y copias. **AC-10.4:** el historial auditado no se edita desde funciones ordinarias; retención y eliminación se rigen por la política aprobada | RF-01/02; política de retención y verificación de identidad |

## No funcionales

Los números de rendimiento, capacidad y disponibilidad se fijarán con un perfil de carga y presupuesto aprobados. Las puertas siguientes son verificables sin inventar un SLA.

| ID | Requisito | Evidencia de aceptación |
|---|---|---|
| RNF-01 · Aislamiento | Autorizar por rol y pertenencia en cada operación; denegar por defecto | Matriz de pruebas con usuario A, usuario B, administrador y sesión inválida; ningún dato privado cruza cuentas |
| RNF-02 · Integridad | Operaciones críticas atómicas, idempotentes y con control de concurrencia | Reintento tras respuesta perdida, dos dispositivos simultáneos y caída antes/después de confirmar; un resultado de negocio |
| RNF-03 · Tiempo | Separar instante UTC, fecha local de negocio y zona de agenda | Casos de medianoche, cambio de zona y cambio horario; reproducción del resultado histórico |
| RNF-04 · Accesibilidad | Formularios, gráficos y estados utilizables con teclado, lector y sin depender del color | Revisión de flujos RF-01 a RF-05 según [diseño](../diseno/README.md), con incidencias resueltas o documentadas |
| RNF-05 · Privacidad | Minimizar captura y separar uso personal, biometría y telemetría técnica | Revisión de campos, consentimiento revocado en tareas pendientes y ausencia de tokens/datos sensibles en logs |
| RNF-06 · Rendimiento | Medir latencia y capacidad del flujo prioritario antes de fijar objetivos | Perfil reproducible: usuarios simultáneos, tamaño de historial, p95, errores, recursos y objetivo aprobado en decisión D-08 |
| RNF-07 · Recuperación | Poder restaurar datos persistentes y reconciliar trabajos | Ejercicio de restauración en entorno aislado; RPO/RTO medidos y comparados con objetivos pendientes de aprobar |
| RNF-08 · Mantenibilidad | Un contrato y reglas de negocio compartidos por clientes | Cambios de contrato revisados, generación/validación de tipos y pruebas de compatibilidad; sin lógica divergente por pantalla |
| RNF-09 · Observabilidad | Identificar fallos de solicitudes y trabajos sin exponer datos personales | Traza correlacionada de registro y recálculo; alertas con responsable y procedimiento de atención |
| RNF-10 · Reproducibilidad | Documentar herramientas, versiones, variables y comandos reales | Un integrante levanta la entrega desde un clon limpio con datos sintéticos y obtiene las verificaciones documentadas |

## Puerta del primer flujo

Una entrega de RF-01 a RF-05 necesita además RNF-01/02/03/04/05/08/09/10. Antes de un piloto con datos personales también debe existir una solución probada para RF-10, restauración, suspensión y políticas de conservación. Implementar primero la interfaz no exonera estas condiciones.
